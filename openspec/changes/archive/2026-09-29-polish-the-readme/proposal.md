## Why

Bean `specgetty-mobile-4l3a`.

The README is 211 lines of accurate reference material with no landing page in
front of it. It has no badges, no images, and until an hour ago no install path
except building the APK yourself. `add-continuous-integration` removed that last
excuse: there are six badges to show and a signed APK at `v0.1.0` to link.

The reference material is good. That decides the shape of this change: very
little needs writing, and what is missing is the page a newcomer meets first.

Three things cost the most, in order.

**Nothing shows what the app looks like.** Zero images in 211 lines, for an app
whose whole value is how it renders a spec on a phone. Five screenshots already
sit in `fastlane/metadata/`, published to a store nobody has been sent to yet,
and the README does not use them.

**The reader is told what before why.** The file opens on "What it does" and a
feature list. Why anyone would read specifications on a phone is never said.

**The contributor tail outweighs the newcomer.** The gate, how the parsers were
derived and the store edge case take 47 lines, ahead of the roadmap and the
licence. The gate section spends 26 lines asserting in prose what a Check badge
and a coverage badge now assert in the header.

Against the consensus of the READMEs on
[awesome-readme](https://github.com/matiassingers/awesome-readme), what is
missing is badges, an image, a contributing section, and a line saying what else
exists around the format.

## What Changes

**The README stays one file.** specgetty split its README into five `docs/`
pages, and that does not transfer: `fdroid-readiness` asserts what this README
says in six scenarios, each beginning "WHEN the README is read". Moving the
token section into `docs/` would make one of them false. Splitting is therefore
a spec change rather than a documentation move, and it is not worth making now.
The room comes from tightening instead.

| section          | now | after | why                                          |
|------------------|-----|-------|----------------------------------------------|
| The gate         |  26 |     8 | the Check and coverage badges say it better  |
| Several projects |  27 |    12 | feature detail, not a landing page           |
| Points at a store|  10 |     5 | an edge case                                 |
| How it is built  |  11 |     5 | provenance, worth a paragraph not a section  |

That pays for a badge block, a hero, a why, a screenshot strip, contributing and
related, and leaves the file about where it started.

**A hero recording, of stepping through a spec.** The app gained next and
previous on a spec card in `spec-card-next-and-previous`, and that is the thing
a still cannot show: an outline, a card, and a reader moving through requirement
and scenarios without going back. It is also the good case for a looping image,
because the frames between taps are identical and compress to nothing.

**Imagery stays on API 26, after an attempt to move it.** The intent was to
photograph the app on API 36, on the grounds that the version a regression shows
up on first says nothing about what the app should look like in a picture. The
attempt failed on something bigger: the instrumented suite does not run on API
36 at all. Every test that adds a repository times out, including the one that
only needs an error message to appear, and the failure predates this change.
There is no app-side exception and no cleartext error, so the cause is not
obvious and finding it is not this change's job. It is
`specgetty-mobile-ityo`.

What survives is the part that was worth having anyway: `scripts/emulator.sh`
takes an API level instead of hard-coding one, each AVD keeps its own log, pid
and serial so that starting one does not make the other unkillable, and the
suite names the emulator it wants rather than taking whichever of ours it finds.
That is what the investigation will need.

**The screenshot set grows by the two that matter.** The five are repositories,
the overview, the changes, the tasks and a difference. Missing are the spec card,
which is what the app is for, and the two-pane adaptive layout, which is what it
looks like on a tablet. Everything is being retaken anyway.

**Installation leads with the release.** A downloaded APK first, the build
command second. The build command stays because `fdroid-readiness` requires it,
not merely because it is useful.

Not in scope, with the reason for each:

- **A `docs/` split.** Deliberate, for the reason above. When the README next
  outgrows itself, the spec gets reworded first and the split follows.
- **F-Droid submission, or an F-Droid badge.** There is no listing to badge.
- **Retaking the recording on every change.** It is regenerated by a command, the
  way the screenshots are, not on a schedule.

## Capabilities

### Modified Capabilities

- `fdroid-readiness`: the README gains a way to get a built APK rather than only
  a way to build one; a published recording is held to the same standard as a
  published screenshot; and the audit records which Android version the imagery
  was taken on, now that it differs from the one the tests run on.
- `end-to-end`: the project can now start emulators at other API levels, so
  "targets its own and leaves the other alone" has to mean the API 26 one
  specifically rather than whichever of ours is up.

### New Capabilities

None. The recording could have justified a capability of its own, and it is left
in `fdroid-readiness` on purpose: that spec already owns both the README and the
screenshots, and putting the hero somewhere else would separate it from the
images it is recorded beside.

## Impact

- `README.md`: restructured, roughly the same length
- `flake.nix`: `ffmpeg` into the emulator shell, so the recording is not a thing
  only one machine can produce
- `scripts/emulator.sh`: an API argument, so the imagery AVD and the test AVD can
  differ
- `scripts/recording.sh`: new, mirroring `scripts/screenshots.sh`
- the screenshot test: two more shots, and a run that can be recorded
- `fastlane/metadata/.../phoneScreenshots/`: all retaken, two added
- `docs/fdroid.md`: the API level the imagery was taken on, and why it is the
  same one the tests use
- `specgetty-mobile-4l3a`: closed by this

## Rollback

Its own commit. The images are files, the scripts are additive, and reverting
restores a README that was accurate and plain. Nothing in the app changes, so
nothing in the app can break with it.
