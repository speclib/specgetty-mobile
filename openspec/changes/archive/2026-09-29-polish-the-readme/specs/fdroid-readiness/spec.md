## MODIFIED Requirements

### Requirement: The README tells a newcomer what to do

The README SHALL say what the app is, how to build it, how to install it, how to
add a repository and a token, and what is planned next.

Installing SHALL cover getting a built APK as well as building one. A reader who
wants to try the app is not asking to set up a toolchain, and a released APK now
exists for them.

#### Scenario: Building

- **WHEN** the README is read
- **THEN** it gives the command that produces an APK

#### Scenario: Downloading one instead

- **WHEN** the README is read
- **THEN** it says where a signed APK can be downloaded, and that is the first
  way offered rather than the last

#### Scenario: Installing

- **WHEN** the README is read
- **THEN** it says how to get that APK onto a phone

#### Scenario: Adding a repository

- **WHEN** the README is read
- **THEN** it says what a URL may look like and that a page URL is normalised

#### Scenario: The token

- **WHEN** the README is read
- **THEN** it says a token is typed rather than captured, and how it is kept

#### Scenario: What is not in this version

- **WHEN** the README is read
- **THEN** it says this version reads and names what Phase 2 adds

### Requirement: The store listing exists and does not overstate

The project SHALL provide Fastlane metadata for the default locale, and every
screenshot it ships SHALL have been taken from the running app rather than
composed by hand.

The project SHALL record which Android version its screenshots were taken on,
because a reader comparing a screenshot with their own phone has no other way to
know what they are looking at.

#### Scenario: The metadata

- **WHEN** `fastlane/metadata/android/en-US/` is read
- **THEN** it holds a title, a short description, a full description and a
  changelog for version 1

#### Scenario: Screenshots

- **WHEN** the screenshots directory is read
- **THEN** it holds images taken by driving the app on an emulator

#### Scenario: Which Android they show

- **WHEN** the audit is read
- **THEN** it says which Android version the screenshots were taken on

#### Scenario: Taking them again

- **WHEN** the app's appearance changes
- **THEN** the screenshots can be regenerated by one command rather than redrawn

#### Scenario: What is photographed

- **WHEN** a screenshot is taken
- **THEN** the project in it was written by the test, not taken from somebody's
  repository

#### Scenario: What the description claims

- **WHEN** the full description is read
- **THEN** it says this version reads and does not edit

## ADDED Requirements

### Requirement: A published recording is held to the standard a screenshot is

The project SHALL hold any moving image it publishes to the same rules as a
still one: driven from the running app, showing a project the test wrote, and
reproducible by one command rather than recaptured by hand.

A recording is the more tempting thing to fake, because a still can be checked
by looking at it and a recording is watched once. The rules are therefore the
same rules, stated rather than assumed.

#### Scenario: How it was made

- **WHEN** the recording published in the README is traced back
- **THEN** it was produced by driving the running app, not assembled from stills
  or drawn

#### Scenario: What it shows

- **WHEN** the recording plays
- **THEN** the project in it was written by the test, as a screenshot's is

#### Scenario: Making it again

- **WHEN** the app's appearance changes
- **THEN** the recording can be regenerated by one command

#### Scenario: What it costs the reader

- **WHEN** the README is opened
- **THEN** the recording it loads is small enough that the page is not the thing
  the reader waits for

#### Scenario: A machine that is not this one

- **WHEN** somebody else runs the command that produces it
- **THEN** everything it needs comes from the project's own environment rather
  than from whatever happens to be installed
